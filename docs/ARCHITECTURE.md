# Architecture

> Status: Current · How WolfCmd fits together ([ADR-0001](adr/0001-founding-architecture.md)). Describes only what exists.

## The shape
```
WolfCmd.exe (crates/wcmd-app, Tauri 2)
├─ window: frameless with our title bar (Snap Layouts overlay on Windows; native traffic lights over it on macOS, `tauri.macos.conf.json`), WebView2 hardened (platform/: Windows, with stubs and the desktop opener for macOS and Linux)
├─ terminals: one ConPTY shell per panel, outliving the page; VT state kept for reattach and scrollback (session/)
├─ watchdog: reloads a page that stopped answering (watchdog.rs); terminals keep running
├─ tray: closing the window hides it to the tray (tray.rs; macOS: the Dock); Quit is the tray's menu or Ctrl+Q
├─ state: the workspace document and window bounds, saved crash-safe (state.rs)
├─ settings: settings.toml (wcmd-config); N-07 the default shell setting picks a new terminal's shell
├─ agents: the registry (built-ins + N-09 plugin agents from <data dir>/plugins) and the line that starts or resumes an agent (wcmd-agents)
└─ git: a workspace's worktrees: list, add, remove (git.rs), hidden, no prompts, with a timeout
        ▲ 26 IPC commands, five events (ipc/), generated TS bindings
        ▼
UI (packages/app, React) — owns the live document (workspaces → tabs → tiled panels) and edits it
```

## Crates (one-way dependencies, top uses bottom)
| Crate | Job |
|---|---|
| `wcmd-app` | The app: window, IPC, session host, state service, git worktrees. Depends on all below |
| `wcmd-agents` | Agent registry (`resources/agents/*.toml` + N-09 plugins: `<data dir>/plugins/<id>/plugin.toml`, data only, read again only when the folder changed; problems reported, ids never shared), locating the CLI, start/resume lines (`--session-id` for Claude Code, resume-or-new for a never-saved session, the picker for a second id-less panel, Remote Control) |
| `wcmd-state` | The document (`Document` → `Workspace` (name, optional folder, N-10 optional `main`: a worktree's main workspace) → `Tab` (N-03 optional `maximized` panel) → `Layout` of splits and `Panel` leaves; N-03 a panel's `content` is tagged by its `kind`: `terminal`, or an unknown kind kept untouched) with `normalized()`, `workspaces.json` (careful load, migrations of older formats, backups) and `window.json` files |
| `wcmd-pty` | ConPTY sessions (patched portable-pty in `third_party/`), shell profiles, shell integration scripts |
| `wcmd-term` | VT state (alacritty_terminal): the replay a reattached view starts with, and the scrollback snapshot |
| `wcmd-config` | `settings.toml`, and `fs::write_atomic` (crash-safe whole-file writes) used by every saved file |

Class lists use only the token scales (the `wolfcmd/design-tokens` ESLint rule, `tools/eslint/`), and a test checks every text and icon color's contrast in both themes.

## The window
- **Look (N-01, [ui-kit](../packages/ui-kit/CLAUDE.md)):** WolfCmd's own design, calm and warm, the same on every OS: a warm neutral ramp, soft rounded shapes, diffuse shadows, monochrome-first chrome with one sparing accent (a light blue-violet), Lucide line icons, the system UI font. Dark by default (`[appearance] theme`: Dark, Light or Auto; `data-theme` on the page, Auto following the system live, and the native window's theme; the tokens follow it). The terminals keep the Dark Modern and Light terminal palettes. Panels are rounded blocks with a slim header on the window background; the focused one has an accent border, the one sign of where the keyboard is (the workspace's color shows on the switcher's dot, stable per workspace, a worktree sharing its main's). Menus and flyouts are opaque. Below 1280 px wide the chrome is compact (`chrome/density.ts`).
- **Title bar:** the workspace switcher (with the workspace's color as a dot), the shown workspace's tabs as fixed-width pills, the window's buttons. Per OS (`chrome/title-bar.ts`, the only layout difference): on Windows our caption buttons with Snap Layouts on maximize (`platform/caption.rs`), on Linux our caption buttons, on macOS the native traffic lights (`titleBarStyle: "Overlay"`, hidden title, in `tauri.macos.conf.json`) with room left for them at the bar's start. The window's background is the theme's `--wc-bg-subtle` (`startup.rs`, `tauri.conf.json`).
- **Right bar (N-06):** a slim bar on the right edge drawing the items registered in `chrome/bar.ts` (no item is known by name): + on top, then Agents; plugins' buttons later; N-07 items placed `bottom` sit at its foot (Settings). + opens the Add flyout, which lists the "add entries" registered in `chrome/add-entries.ts`: today Terminal (the default shell, or a chosen installed shell). It is the seam for more panel kinds: each panel type (N-03, `panels/types.ts`: its kind, view, header and add entry) registers an entry there ([guide](guides/panel-types.md)).

## Flows
- **Start:** the core sets an earlier data folder of a different format aside as `<name>.old`, loads `workspaces.json` (normalized) and `window.json`, and opens the hidden window at its saved place. The UI loads the document and settings, renders, then calls `app_window_ready` and the window shows.
- **Loading the workspaces (never lose them):** only a missing file is a fresh start. A file that can't be read is retried, then the run is read-only (nothing is saved, the file stays as it is) and the newest good backup is shown; a damaged file is copied aside as `workspaces.broken-<seconds>.json` and the newest good backup opens (read-only when the copy fails); a file from a newer WolfCmd is shown read-only and never overwritten. A good file is copied to the backups. `StateService::is_fallback()` tells per-panel cleanup that the document did not come from a good file.
- **A change:** a user action builds the next document with `model/`, the store sets it and calls `state_save` with the page's number for it (`seq`: invokes may run in any order, so the core applies only a newer one; a page load starts again from 1); the core's writer thread writes it at once with `write_atomic` (the newest wins when changes come faster than the disk). A failed write is kept and retried (200 ms doubling to 5 s) unless a newer document replaced it; the `state-health` event (`StateHealth`, also in `state_load`) makes the UI show a calm notice under the title bar until a save succeeds, and says why a run is read-only. When Windows ends the user session (`WM_QUERYENDSESSION`) and on quit the core stops writing later documents (an agent the shutdown ends is not saved as ended; a cancelled shutdown writes the newest and goes on), flushes the queue (waiting for the writer at most 5 s, then writing on the quitting thread) and every terminal's scrollback.
- **A terminal:** the panel mounts an xterm view and calls `pty_open` with the panel ID: the core attaches it to the panel's running shell (the stream starts with a replay of the screen, scrollback, modes and title, then the output after it, each byte exactly once) or starts one. Output streams as raw bytes on a channel into `term.write` (flow control: the UI acks in 128 KiB steps, the reader pauses above 8 MiB; with no view attached it never pauses). Keystrokes carry a per-view sequence number, so the core writes them in order, once. A new shell of a restored panel first shows its saved scrollback, dim, above a divider. The shell's folder is reported (`{ cwd }`) only when it changes.
- **In a terminal (`terminal/terminal-view.ts`, outside React):** OSC 133 marks drive the shell phase (Shift+Enter, agent readiness) and the command marks (`terminal/marks.ts`: the last 500 commands as xterm markers; gutter dots, slim lines on the scrollbar's track (the overview ruler, at the panel's right edge), Ctrl+Up/Down, the sticky header painted through a ref, a command's menu); nothing runs per output chunk. OSC 9 / 777, the bell and long or watched commands ask for attention and OSC 9;4 reports progress: the panel puts them in `store/attention.ts` (ignored while the user looks at the panel, cleared by looking), the panel header shows a bell and a progress bar, the tab pill a dot. Find uses xterm's search addon (one command's output: `terminal/scoped-find.ts`). A Ctrl+clicked link (Cmd+click on macOS) goes to `app_open_link` with the file's line, column and the shell's folder; the core (`open.rs`) opens URLs and files, shows executables in the file manager and never runs them. Pastes with a line break into a shell without bracketed paste wait for the user's OK; a picture pasted into an agent panel presses the agent's `image_paste` key. Files dropped on the window come from Tauri's native drag events (`core/drops.ts`); `panels/file-drops.ts` finds the panel under the pointer and it types the quoted paths (`terminal/drop.ts`, by the profile that runs). The Kitty keyboard protocol answers programs only with `terminal.kitty_keyboard` on.
- **Resizing a terminal (N-03, never a blink):** the view's `ResizeObserver` fits xterm inside the observer callback, before the frame is painted (once per frame, never a frame late), and `terminal/paint.ts` then renders the rows at once: a canvas whose size changed is empty until drawn, and xterm would draw only at the next frame. The same happens after xterm's own device-pixel resize of the WebGL canvas (an observer created after xterm's, `terminal/gpu.ts`), when a terminal comes back on screen (an `IntersectionObserver` after xterm's) and when a shown terminal takes its WebGL context back (`TerminalPanel` calls `setVisible` in a layout effect). A hidden or 0×0 terminal (other tab, minimized) keeps its size. The PTY learns the new size once it stayed the same for 100 ms (two frames after a released divider) and only when it differs from the shell's, so the shell reflows once. The window and web view background is the panel area's `--wc-bg-subtle` for the theme setting (the core at start, `core/app.ts` `followWindowBackground` after a theme change), so a resize never uncovers another color.
- **Rendering a change:** the store replaces the document only when a change changed something (`changePanel` returns the same document otherwise). `TabView` re-renders the cards a change touches: cards are memoized (their box compared by value), callbacks are shared and keyed by panel ID, each tab's geometry is cached by its layout and the area, and a divider drag moves panels from local shares, saving once on release.
- **Panel types (N-03, [design](design/N-03-panel-types.md)):** a panel's saved `content` names its kind. `TabView` looks the kind up in the panel-type registry and draws the type's header (the shared `PanelHeader` with the type's title and icon) and view; a kind nobody registered (a newer WolfCmd's, a plugin's that isn't installed) gets a calm card ("This panel needs a newer WolfCmd" / "the plugin X", Close) and its content is saved back untouched. Only terminal panels have sessions.
- **Older files (N-03):** the core migrates an older `workspaces.json` on load (`migrate.rs`, step by step on the JSON); the first time, the file's bytes are kept as `workspaces.v<format>-<seconds>.json` and the migrated document is written at once (a failed copy makes the run read-only).
- **A terminal's life:** a session outlives its view. Unmounting a view (React's second mount, a reload, a crash) only detaches; the session ends when its panel leaves the saved document (`state_save` compares the terminal panels' IDs), 30 s after its view left when its panel is gone, when its shell exits, or on quit. A reattached agent panel never retypes its start line. Scrollback is saved 5 s after a session goes quiet (15 s at the latest), when it ends, on quit and when Windows ends the user session.
- **Watchdog:** while the window is shown, the core asks the page for a sign of life every 2 s (`window.__wcPing()` → `app_pong`); 10 s of silence (30 s for a page still loading, doubled after each reload it never answered, up to 16 times) is logged and the page reloads. A crashed or unresponsive WebView2 renderer reloads too. Nothing runs while the window is minimized or hidden (N-01: hidden to the tray too); `WOLFCMD_WATCHDOG=0` turns it off.
- **Closing and quitting (N-01):** closing the window (its ✕, Alt+F4, the taskbar's Close) hides it to a tray icon (`tray.rs`: the app's icon, "WolfCmd"; a left click shows the window where it was, the right-click menu has Show WolfCmd and Quit WolfCmd) and everything keeps running: terminals, agents, their activity and the finish notification (its click shows the window and the panel). A hidden page is throttled, so no session waits for its acknowledgements then (`LocalSessionHost::set_background`); a view that falls 8 MiB behind gets nothing more (bounded memory) and, when the window shows, a reset and the screen replay a reattach gets, the stream going on from that offset (each byte still once). The pure close decision (`tray::decide`) hides only for the window's own close with `window.close_to_tray` on (default) and something to bring it back; a quit, the setting off, or no tray (a Linux desktop without one) closes and quits. Quit (the tray's menu, Ctrl+Q / Cmd+Q through `app_quit`) exits through the same path as before: the state frozen and flushed, the scrollback saved, every shell ended. A second launch shows the hidden window (single instance), and Windows ending the user session saves as always (a hidden window gets `WM_QUERYENDSESSION` too). The first hide sends `window-hidden`: the UI shows one calm notice for the window's return ("still running in the tray…", `chrome/tray-hint.ts`) and remembers it (`window.tray_hint_shown`). macOS follows its convention: the red button hides the window, the Dock icon brings it back (`RunEvent::Reopen`, `platform::is_reopen`), no tray icon.
- **Plugins (N-09):** a plugin is a folder `<data dir>/plugins/<id>/` with a `plugin.toml` (id = folder name, name, version, `[[agents]]` shaped like the built-in TOMLs). WolfCmd never runs plugin code. The `AgentRegistry` (Tauri state) compares the folder's fingerprint (the listing, each manifest's modified time and size) when `agent_list` or `agent_command` asks, and parses it again only when it changed; the UI asks when the Agents menu opens, nothing watches or polls the folder. What can't be used (a broken manifest, a bad entry, an id a built-in or an earlier plugin already has) is skipped and listed in `agent_list`'s `problems`; the menu shows one calm line with the details in its tooltip ([guide](guides/plugins.md)).
- **An agent:** the Agents menu opens a panel with `agent: { agent, session, cwd, running: true }` (a new UUID when the agent takes `--session-id`; `cwd` is corrected to the shell's folder when the agent starts). When a shell the view started is ready (its first prompt for an integrated shell, however long that takes; 5 s for one without integration) the panel asks `agent_command` for the line, quoted for the shell `pty_open` really started (`profileId`), with Remote Control when the project or setting says so, and types it as the agent's line (`pty_write` with `agent`).
- **Agent activity (N-06, [design](design/N-06-agent-activity.md)):** while an agent panel's agent runs, the core's session reader watches whether it works, from what the terminal already sees (no hooks): the agent's own title when its TOML has a `working_title` regex (Claude Code `◐`/`◑`, Codex's Braille spinner, Gemini's `✦`/`⏲`; once matched, the title alone decides), else output activity (output more than 300 ms after the last input, lasting 1 s, counted only after the user submitted something since the agent started; 2 s without it is idle, seen at the session keeper's existing 1 s tick). Input times are atomics (`session/activity.rs` `InputMarks`), so keystrokes never wait. Changes go to the page as the `agent-activity` event (also for panels nobody shows) and `pty_open` returns `agentWorking`. The UI (`chrome/agent-activity.ts`, `store/activity.ts`) makes a finish the user didn't see "finished": the header's check until the panel is looked at, the pill's glow (once per unseen finish, in the finished agent's color: the latest finisher's when several did, `--wc-glow-agent`, `--wc-dur-glow`, none under reduced motion) and check in that color until its tab is shown, the finished agent's panel glowing once in its color (`chrome/finish-glow.ts` rules, a pending glow per panel played by the card's `panels/PanelGlow` through a ref: at once when it is on screen and not focused, else when it comes on screen; never for the focused panel; `appearance.finish_glow`), the workspace switcher's row and dot for hidden workspaces. With the window behind, `agent_done` flashes the taskbar button (`platform::flash_taskbar`) and, with `agents.notify_when_done`, shows a Windows toast with the agent's and tab's names only (`platform::notify`, WinRT through the `windows` crate); clicking it brings the window forward and sends `show-panel`.
- **An agent across a restart (never lose the session):** a restored panel starts its shell in the agent's folder (agents keep sessions per folder) and types the line only while `running`. With a session ID it resumes it, or, when the agent never saved it (`resume_or_new`, verified against the CLI), starts a new session with the same ID (`resume || new`); without one (Codex) the first panel of that agent and folder continues the latest session and the others open the agent's picker. The core watches the shell's prompt marks (OSC 133;A): the prompt after the agent's line means the agent ended, reported on the stream (`agentExited`) and to a view that attaches later; the panel then saves `running: false`, so the next start is a plain shell.
- **Workspaces and tabs:** the title bar shows the shown workspace's name (its switcher) and its tabs as pills. A pill dragged sideways (past a few pixels) lifts and follows the pointer, the others make room; the drop is one `moveTab`, Esc puts it back. A workspace's folder is where new terminals start and what Remote Control choices are keyed by.
- **Context menus (N-03):** tab pills, panel headers, terminals and workspace rows have a context menu (ui-kit `ContextMenu`: `Menu`'s items at a point; a `Menu` item's own `contextMenu` opens over its menu). The items are pure functions (`chrome/context-menus.ts`). Shift+F10 and the Menu key are caught by `keys.ts`, which sends the focused element a `contextmenu` marked as the keyboard's and suppresses the browser's own. In a terminal a plain right-click copies or pastes on Windows and opens the menu elsewhere; Shift+right-click and the keys always open it; a program tracking the mouse gets a plain right-click (`terminal/context-menu.ts`). Nothing on empty chrome ([design](design/N-03-context-menus-and-maximize.md)).
- **Maximizing a panel (N-03):** `Tab.maximized` (saved) names the panel that fills its tab; `TabView` parks the tab's other cards like a hidden tab's (same size, off screen, `setVisible(false)`), never unmounting them. A split, a drop (or the start of a header drag), closing it and focusing a hidden panel end it; Esc doesn't. The header shows Restore and the pill a quiet mark.
- **Moving a panel (N-03):** a panel's header dragged past a few pixels shows its name under the pointer and the drop zone under it (`model/drop.ts`: within a quarter of a panel's edge, that half: split there; else the whole panel: swap). The drag paints through refs once a frame, never through React state; the drop is one document change (`dropPanel`), and the panel keeps its ID, so its card and terminal stay mounted and its shell keeps running. Esc or a lost pointer cancels. Pointer events only: native file drops (Explorer) stay the terminal's.
- **Settings (N-07, [design](design/N-07-settings.md)):** one dialog (`chrome/SettingsDialog.tsx` on ui-kit `Dialog`), opened by the bar's foot button, Ctrl+, (Cmd+, on macOS) or the workspace menu (`chrome/settings-open.ts`). Every control applies at once through the settings store (`store/settings.ts`), which saves one change at a time and then only the newest (`settings_save`, `write_atomic`); there is only Close. Terminals restyle live (`data-theme` and `setLook`). The default shell (`terminal.default_profile`) is read by the core at each terminal start: `WOLFCMD_DEFAULT_PROFILE`, then the setting when installed, then the first installed shell (`wcmd_pty::default_profile_preferring`); the profile list's default mark follows it. Font suggestions are known monospace families measured on a canvas (`chrome/fonts.ts`), nothing asks the system. About shows the version and the data folder (`app_about`), which `app_open_data_folder` opens.
- **Git worktrees (N-10):** a worktree is a workspace whose folder is the worktree and whose `main` is its repository's main workspace (`normalized()` clears a link to a missing workspace or to another worktree). When the workspace menu opens, the UI asks `git_worktrees` for each plain workspace's folder (never polled; the last answer is kept, so the menu opens with it): each workspace lists its worktree workspaces under it, then the repository's other worktrees (a workspace is made when one is chosen). New worktree… runs `git_worktree_add` (a new branch from the main tree's HEAD or an existing branch; by default at `<parent>\<repo>.worktrees\<branch>`), then opens the workspace, empty or with copies of the main workspace's tabs (fresh IDs, folders inside the main tree moved to the same place in the worktree, agent panels as fresh agents with new sessions). Remove worktree… runs `git_worktree_remove`: the core refuses the main tree, and a tree with changes or a lock unless forced, then ends the workspace's terminals and waits for their pseudo consoles to close (Windows can't delete a folder a shell stands in), then git removes the folder (the branch stays); the UI closes the workspace after that. Git runs on the blocking pool without a window or prompts, with a timeout; its own message is the error the dialog shows. The title bar says "repo › branch" while a worktree is shown.

## Data files (`%APPDATA%\WolfCmd`, `WolfCmd-dev` in debug, `WOLFCMD_DATA_DIR` in tests)
| File | Written by | Format |
|---|---|---|
| `workspaces.json` | `wcmd-state` | `Document`, version 2 (N-03 panel contents; version 1 is migrated) |
| `workspaces.v1-<seconds>.json` | `wcmd-state` | N-03: a format 1 file as it was, copied before its first migration; never deleted by the app |
| `workspaces.json.bak` | `wcmd-state` | the last good `workspaces.json`, copied at each start |
| `backups/workspaces-<YYYY-MM-DD>.json` | `wcmd-state` | the first good file of each day (UTC); the newest 7 are kept |
| `workspaces.broken-<seconds>.json` | `wcmd-state` | a copy of a damaged `workspaces.json`, never deleted by the app |
| `window.json` | `wcmd-state` | `WindowBounds` |
| `settings.toml` | `wcmd-config` | version 1; read once at start (only a missing file means defaults; an unreadable one makes the run's settings read-only) |
| `settings.broken-<seconds>.toml` | `wcmd-config` | a copy of a `settings.toml` that didn't parse, never deleted by the app |
| `scrollback/<panel>.snap` | `wcmd-app` session | `wcmd_term::snapshot` (a fallback document never cleans them up) |
| `shell-integration/` | `wcmd-pty` | scripts, rewritten when changed |
| `plugins/<id>/plugin.toml` | the user (read by `wcmd-agents`) | N-09 plugin manifest; never written by WolfCmd |

## Tests
Unit tests sit next to the code (Vitest, `cargo test`; `pnpm check`). `tests/e2e` (`pnpm e2e`, not in `pnpm check`) starts the real `WolfCmd.exe` on a fresh data folder and drives its page over the DevTools protocol: terminals, splits, tabs, workspaces, reload, crash and restart, damaged files, window bounds, agents ([its notes](../tests/e2e/CLAUDE.md)).
